## Exam task 3.6: Storage services

### S3 objects, buckets, and access

Amazon S3 is object storage. A bucket contains objects; an object has content, a key, metadata, and potentially a version identifier. The key identifies it within the bucket. Console folders generally organize key prefixes rather than creating a traditional disk filesystem.

Typical uses include static website assets, media, backups, logs, archives, and data lakes. S3 does not execute server-side application code merely because it can host a static site. HTML, CSS, JavaScript, and images are the course's examples.

#### Recorded limits versus current documentation

The video states a 5 TB maximum object size. **Update:** Current [S3 object documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingObjects.html) describes objects up to 50 TB, with a more precise limit noted there. Do not memorize the recorded number as a current universal limit. Large overall storage scale does not remove per-object, request, or service limits.

The demo's globally unique bucket name describes the familiar shared namespace. **Exam extension:** Naming scope depends on bucket type/namespace and AWS partition; newer naming options exist. Use the applicable [bucket naming rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html) for a real deployment. The exam priority is bucket versus object, not exhaustive naming syntax.

#### Security remains customer work

The reading introduces resource-based bucket policies, identity-based policies, and encryption. The video adds presigned URLs, access points, and audit visibility.

- Bucket policies attach permissions to the resource; identity policies attach permissions to identities.
- A presigned URL grants time-limited access under the signer's effective permissions; it does not require making the bucket publicly readable.
- Access points can provide distinct access arrangements for shared datasets.
- Encryption at rest and protected transport complement permissions; neither grants safe access configuration automatically.

The demo's Block Public Access settings block public access configurations, not every form of authorized external or cross-account access. Its statement that only the object creator can access data is too simplistic: ownership, IAM, resource policies, and account controls determine authorization.

**Exam extension:** Versioning preserves object versions and can assist recovery from unintended changes. It is not unlimited immunity to deletion: authorized permanent version deletion, lifecycle configuration, and retention choices matter. Logs also require appropriate configuration and interpretation; a generic claim of complete logging of every request is not a substitute for a logging design.

### Durability, availability, and recoverability

| Concept | Meaning | What it does not guarantee |
|---|---|---|
| Durability | Protection against loss of stored data | Every request always succeeds instantly |
| Availability | Access to the service/data when needed | Recovery of every accidentally deleted item |
| Backup and retention | Preserve recoverable earlier states | Automatic restoration of a complete working application |

The course emphasizes eleven nines of designed S3 durability. That is not an availability percentage or an individual-object promise against every customer action. One Zone choices also have different exposure to loss of an AZ. Read the class's resilience model rather than assuming every S3 object is stored across multiple AZs.

*Adapted study material; [Module 6, section 6 (course background)](https://www.coursera.org/learn/aws-cloud-practitioner-essentials/lecture/6Bz4a/introduction-to-storage).*

### Choose an S3 storage class

| Class introduced | Main fit | Main tradeoff |
|---|---|---|
| Standard | Frequently accessed general-purpose data | Storage cost versus colder alternatives |
| Intelligent-Tiering | Unknown or changing access patterns | Automatic access-based tiering with applicable monitoring/feature charges |
| Standard-IA | Infrequent access needing rapid retrieval | Retrieval fees and minimum-duration considerations |
| One Zone-IA | Infrequent, re-creatable data | Single-AZ exposure |
| Express One Zone | Latency-sensitive, frequently accessed objects | Specialized single-AZ design; not simply an inexpensive archive |
| Glacier Instant Retrieval | Rare access needing milliseconds retrieval | Retrieval and duration economics |
| Glacier Flexible Retrieval | Archives tolerating minutes-to-hours retrieval | Restore workflow rather than immediate access |
| Glacier Deep Archive | Long retention with substantial retrieval delay acceptable | Longer restore delay |
| S3 on Outposts | Object storage at an Outposts site | Local deployment requirements |

The course's general distinction is access frequency, required retrieval speed, resilience, and cost. An archive label does not mean every Glacier option has the same retrieval behavior. See [S3 storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html).

Glacier Instant Retrieval permits real-time access. Flexible Retrieval and Deep Archive require restoration before ordinary object retrieval. Restore timing depends on the chosen option; “Deep Archive always returns within 12 hours” is too absolute. Minimum storage durations and retrieval charges can affect total cost, so the lowest storage rate may not be the lowest workload cost. See [Glacier comparison](https://docs.aws.amazon.com/AmazonS3/latest/userguide/glacier-storage-classes.html).

The video gives an incorrect fixed count for Intelligent-Tiering's tiers. **Qualification:** It has automatic frequent, infrequent, and archive-instant tiers, plus optional archive-access tiers. Learn the automatic access-pattern concept rather than the recorded count. See [Intelligent-Tiering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intelligent-tiering-overview.html).

*Adapted study material; [Module 6, section 7 (course background)](https://www.coursera.org/learn/aws-cloud-practitioner-essentials/lecture/6Bz4a/introduction-to-storage).*

### Lifecycle is not the same as access-based tiering

S3 Lifecycle can transition eligible objects and expire objects or versions under configured rules. It suits predictable retention: logs become older, move to a cheaper appropriate class, and eventually reach the retention limit.

**Correction:** The reading describes ordinary Lifecycle transitions as days since the object was last accessed and days spent in each successive class. Standard day-based rules are based on object age, or on version-specific timing for noncurrent versions, rather than simply resetting on reads. The example's day counts must be translated into valid rule semantics. See [Lifecycle timing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html).

Intelligent-Tiering is the choice emphasized for unknown or changing access patterns. EFS lifecycle also has its own access-based behavior. Do not transfer one service's timer rules to another.

Expiration does not have one identical effect for every versioning state. **Exam extension:** In a versioned bucket, expiration of a current version can create a delete marker; separate noncurrent-version rules govern old versions. Lifecycle is a data-deletion mechanism, so retention design matters.

### Reconstruct the S3 demonstration

The instructor creates a bucket, selects a Region, retains Block Public Access, uploads files and a folder, examines metadata, and visits object and bucket settings. The demo also illustrates a cross-account upload policy and version history.

| Demo element | Purpose |
|---|---|
| Bucket and object key/prefix | Locate and organize data |
| Properties | Settings such as versioning and encryption |
| Permissions | Identity/resource access and ownership configuration |
| Management | Lifecycle, replication, and inventory features |
| Object properties and versions | Inspect an individual object's state and history |

The takeaway is that placement, authorization, versioning, and lifecycle are separate decisions. A visible object URL does not prove public access. An upload preserving apparent folder structure does not turn S3 into an NFS filesystem. User-defined metadata and object tags are also distinct features, despite the demo's loose wording.

### Select from the requirement

| Scenario | First choice to consider |
|---|---|
| Temporary local scratch data that can be lost | Instance store |
| Persistent disk for a database running on EC2 | EBS |
| Static website objects and media | S3 |
| Shared NFS files across application servers | EFS |
| Windows file server compatibility | FSx for Windows File Server |
| Parallel high-performance filesystem | FSx for Lustre |
| Existing ONTAP/OpenZFS dependency | Matching FSx option |
| Local file interface backed by S3 | S3 File Gateway |
| Local iSCSI storage with cloud integration | Volume Gateway |
| Existing tape backup application | Tape Gateway |
| Replicate servers for recovery in AWS | Elastic Disaster Recovery |

The repair-shop scenario in the video chooses EFS for collaboration. Interpret it as an application needing shared filesystem semantics. Multiple users viewing media over a website could instead use object storage; the access interface decides.

### Exam requirements and service choices

#### Add centralized backup to the storage decision

**AWS Backup** centrally manages data protection for supported resources using backup plans, schedules, retention/lifecycle settings, vaults, and applicable copy policies. A backup plan can select resources, including through tags, so protection does not depend on a person remembering to create each snapshot. Support for cross-account, cross-Region, continuous backup, and restore features varies by resource type; check the specific combination.

A **backup vault** organizes recovery points. A **backup plan** defines the protection policy. A **recovery point** is a retained backup state that can be used in a supported restore workflow. **AWS Backup Vault Lock** can enforce retention controls; it is related recognition detail rather than permission to assume all stored backups are immutable by default.

| Need | Service/feature | Why another storage feature is insufficient |
|---|---|---|
| Central schedules/retention across supported AWS services | AWS Backup | S3 Lifecycle alone is not an organization-wide backup policy |
| Point-in-time backup of an EBS volume | EBS snapshot | A second live volume is not automatically historical recovery |
| Recover overwritten/deleted S3 object versions | S3 Versioning | It must be enabled; permanent version deletion/expiry still needs consideration |
| Retain objects under supported WORM controls | S3 Object Lock | Different from simply retaining several editable/deletable versions |
| Transition old objects or expire them by policy | S3 Lifecycle | Transition/expiry is data lifecycle management, not automatically a backup |
| Replicate supported server workloads for recovery in AWS | AWS Elastic Disaster Recovery | Replication/recovery infrastructure differs from a central backup schedule |

#### Revisit storage boundaries

EBS is persistent block storage with volumes scoped to an AZ; snapshots can support creating volumes in another AZ. Instance store is local, temporary block storage suited to reconstructable data. A reboot normally preserves instance-store data, while stop/hibernate/termination or host failure can lose it. EBS termination behavior depends on volume deletion settings.

EFS provides shared NFS storage, with Regional and One Zone choices whose resilience differs. FSx provides specific managed filesystems, including Windows File Server, Lustre, NetApp ONTAP, and OpenZFS. S3 is API-based object storage rather than an ordinary shared POSIX filesystem. Storage Gateway connects local file, volume, or tape workflows with cloud storage; cached and stored volume modes differ in where primary data is kept.

For S3 classes, distinguish access frequency, retrieval latency, resilience, and total cost. Glacier Instant Retrieval is immediately accessible; Flexible Retrieval and Deep Archive use restoration workflows. A single-AZ class is a different resilience choice from a multi-AZ class. Intelligent-Tiering reacts to access patterns, while ordinary Lifecycle rules act on configured conditions such as age.

**Worked choice:** A company wants daily retained backups of supported EC2/EBS and database resources with centrally applied policies. Choose AWS Backup. A request to move old S3 logs to a cheaper archive class instead points to S3 Lifecycle. A request for local access to cloud-backed files points to S3 File Gateway. These are distinct requirements despite all involving stored data.

Sources: [AWS Backup](https://docs.aws.amazon.com/aws-backup/latest/devguide/whatisbackup.html), [supported backup features](https://docs.aws.amazon.com/aws-backup/latest/devguide/backup-feature-availability.html), [instance-store lifetime](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html), and [S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).
